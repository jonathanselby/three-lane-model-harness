## 1. Executive system description

The repository implements a small Go command-line program that accepts a task and an explicit workload complexity (`simple`, `standard` or `complex`), selects a configured provider/model lane, invokes that provider and emits a structured JSON result containing model output and an execution trace.

The runtime separates routing from provider execution. `internal/harness.Router` owns request validation, lane selection, provider lookup and trace creation. Providers implement one interface with `Name()` and `Generate(...)`. V0.1 includes a deterministic mock provider and an Ollama-compatible HTTP provider.

The caller, not the harness, supplies the complexity class. The code contains no automatic classifier.

No durable application state is present. Configuration and traces are process-local. The CLI supplies a timeout context to provider calls.

## 5. Runtime flows

### Flow A — successful mock request

1. CLI requires `-complexity` and `-prompt`.
2. CLI constructs `Config` with provider/model settings for all three lanes.
3. CLI registers mock and Ollama providers in `harness.New`.
4. CLI creates a timeout context.
5. `Router.Run` creates the initial trace and request ID.
6. Empty task is rejected before lane selection.
7. `laneFor` maps the supplied complexity directly to one configured lane.
8. Router copies lane provider/model into the trace.
9. Router validates provider/model configuration.
10. Router resolves the named provider from its registry.
11. Provider `Generate` executes.
12. Router copies token counts, duration and success state into the trace and returns output + trace.
13. CLI prints indented JSON.

### Flow B — Ollama request

1. Routing selects a lane whose provider name is `ollama`.
2. Ollama provider trims/configures its base URL and uses its supplied HTTP client or `http.DefaultClient`.
3. Provider encodes `{model,prompt,stream:false}` as JSON.
4. Provider POSTs to `/api/generate` using the caller context.
5. Non-2xx responses are converted to an error including status and response body text.
6. Successful response JSON is decoded.
7. `response`, `prompt_eval_count` and `eval_count` are mapped to provider result fields.
8. Router returns output and trace.

### Flow C — validation/provider failure

The router returns a failed trace for:

- empty task;
- invalid complexity;
- missing provider/model configuration;
- provider name not present in registry;
- provider execution error.

No retry or alternate-lane behaviour is visible in the implementation.

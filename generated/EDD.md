## 1. Executive system description

The repository implements a Go command-line program that accepts a task and one explicit complexity value (`simple`, `standard`, `complex`). It maps that complexity to one configured provider/model lane and invokes a provider through a common interface.

The routing core is provider-agnostic. V0.2 contains five provider implementations:

- `mock` — in-process deterministic provider;
- `ollama` — HTTP adapter for `/api/generate`;
- `azure` — HTTP adapter for Microsoft Foundry / Azure OpenAI v1 Chat Completions;
- `bedrock` — HTTP adapter for Amazon Bedrock Runtime Converse;
- `vertex` — HTTP adapter for Google Vertex AI `generateContent`.

The managed provider adapters use different URLs, authentication headers and payload schemas, but all return the same `provider.Result` to the router.

## 5. Runtime flows

### Flow A — route a request

1. CLI requires `-complexity` and `-prompt`.
2. CLI constructs `Config` with one provider/model pair per lane.
3. CLI registers all provider implementations.
4. CLI creates a timeout context.
5. `Router.Run` creates an execution trace.
6. Empty task is rejected.
7. Complexity is mapped directly to one lane.
8. Empty provider/model configuration is rejected.
9. Provider is looked up by name.
10. `Provider.Generate(ctx, model, task)` is called.
11. Token counts and duration are copied to the trace.
12. Provider failure returns a failed trace; success returns output plus successful trace.

### Flow B — managed cloud provider

1. CLI reads non-secret platform settings from flags/environment.
2. CLI reads credentials from environment variables.
3. Router invokes the chosen provider through the common interface.
4. Provider validates required platform configuration.
5. Provider creates the platform-specific HTTPS request.
6. Provider adds the platform-specific authentication header.
7. Provider performs the request under the router's timeout context.
8. Non-2xx, malformed or empty responses become explicit errors.
9. Text and provider token counts are mapped back into common `provider.Result`.

## 6. State and persistence

All material state is process-local configuration and request state.

There is no database, file-backed result store or persistent trace implementation in the runtime code.

The process-global `requestCounter` participates in request ID creation. Provider configuration and credentials live in process memory for the life of the CLI process.

## 8. External dependencies

The Go module has no third-party runtime SDK dependency for managed clouds. Network calls use the standard library HTTP client.

External runtime dependencies are therefore the configured model endpoints themselves plus the operating environment supplying credentials.

## 10. Failure and recovery behaviour

| Failure | Behaviour | Recovery |
|---|---|---|
| empty task | router rejects | caller correction |
| invalid complexity | router rejects | caller correction |
| incomplete lane | router rejects | configuration correction |
| provider missing | router rejects | register/configure provider |
| missing provider credential/config | provider returns explicit error | deployment correction |
| HTTP non-2xx | provider returns explicit status/body error | none in harness |
| malformed provider JSON | decode error | none in harness |
| no text output | explicit provider error | none in harness |
| timeout/cancellation | context aborts HTTP call | caller/deployment decision |

No retry, failover or circuit breaker is present.

## 11. Security boundaries

- Prompt content crosses from caller into whichever provider the selected lane identifies.
- `Sensitive` is recorded but not evaluated before outbound invocation.
- Managed-cloud credentials enter from process environment and are attached only by the relevant provider adapter.
- The repository does not acquire, rotate or persist credentials.
- Provider error responses are included in returned error strings after an 8 MiB bounded read; deployments should still consider whether upstream error bodies can contain sensitive data.
- There is no policy engine, prompt filter, DLP or injection defence in this codebase.

## 12. Operational behaviour

### Known

- CLI process is short-lived.
- timeout is applied by `context.WithTimeout` and passed through all providers.
- all outputs are JSON at the CLI boundary.
- tracing is request-local and returned to the caller.
- GitHub Actions runs `go test ./...` on repository changes.
- provider tests use local HTTP test servers and do not require cloud credentials.

### Inferred

- cloud credential refresh is expected to be handled by a wrapper/deployment environment because providers accept already-resolved credential strings.
- direct standard-library HTTP was chosen to keep provider SDK dependencies out of the core module; rationale is not recoverable from interfaces alone.

## 13. Known / inferred / unknown

### Known

- the caller explicitly supplies complexity;
- the router contains no provider-specific branches;
- five provider implementations share the same interface;
- cloud provider configuration is isolated to provider construction/adapters;
- secrets are environment-based;
- managed provider contract tests validate HTTP wire behaviour;
- no retries/failover exist.

### Inferred

- provider portability is an intentional design property because adding providers did not modify `Router.Run` or the lane/config types.
- managed credential lifecycle is expected to be external to this program.

### Unknown from implementation alone

- why exactly three lanes were chosen rather than two/four;
- why Azure, Bedrock and Vertex were selected over direct model-vendor APIs;
- intended enterprise governance around credential injection;
- whether production deployments should permit mixed-cloud lanes;
- future retry/failover policy;
- production requirements for streaming, structured output or tool calling.

## 14. Open questions

1. Should credential acquisition remain outside provider adapters permanently, or should future integrations accept credential-provider functions rather than resolved strings?
2. Should provider error-body text be redacted before inclusion in traces/errors?
3. Should streaming require a second provider interface rather than expanding `Generate`?
4. Should future retries be provider-local or an explicit router policy?
5. Is a persistent trace sink a separate concern or a future harness extension?

## 15. Architecture conclusion

The V0.2 code demonstrates a stable core/variable-edge architecture:

```text
CALLER -> THREE-LANE ROUTER -> PROVIDER CONTRACT -> PLATFORM ADAPTER -> MODEL SERVICE
```

The significant observation is negative: Azure, Bedrock and Vertex support was added without changing the router's selection algorithm, request model or provider interface.
